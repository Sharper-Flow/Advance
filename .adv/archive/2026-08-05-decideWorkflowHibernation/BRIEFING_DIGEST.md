- **[archive_only_evidence]** architecture_assessment: Three preconditions gate hibernation. (1) Running-worker signal-set identity has NO native Temporal API: DescribeTaskQueue/Worker-Versioning/Deployments expose operator-assigned Build IDs and eventually-consistent reachability, never the set of registered signal-handler names. A workflow QUERY is a viable point-in-time code-identity probe (queries execute on a live poller with isReplayingHistoryEvents=false) but is sound ONLY under PINNED worker versioning (workflow pinned to one build so query and subsequent signal route to the same code); without versioning it is a racy TOCTOU check. (2) Race-free self-completion IS cheaply satisfiable: a self-completing signal makes the single-threaded workflow the arbiter of its own close; the only residual race (signal arrives during the close window) is handled by server-side UnhandledCommand rollback, and is lossless WHEN a handler exists. Recreate-on-demand is cheap via WorkflowIdReusePolicy.ALLOW_DUPLICATE (default) + signalWithStart. (3) The premise that running-workflow COUNT is the thing to bound is questionable: Temporal has no per-namespace running-count cap, 191 idle workflows is operationally trivial, and the documented cost lever is Active Storage of open histories — which Continue-As-New already bounds and which the official Entity-Workflow + CaN pattern is designed to carry indefinitely. The deeper hibernation risk is silent data loss: a signal sent to a name NO worker build registers is buffered in SDK memory and is SILENTLY DISCARDED when the workflow completes (transient UnhandledCommand during the close race resolves to loss, not stuck); only setDefaultSignalHandler gives visibility. This loss is a real hazard for hibernation specifically because complete-then-recreate widens the window in which the host may emit a signal the (about-to-close / not-yet-recreated) workflow cannot handle.
