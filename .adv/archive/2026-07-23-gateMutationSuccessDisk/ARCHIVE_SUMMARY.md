## Wisdom Accumulated

- **[failure]** Durable-mutation success is gated on Temporal durability only, NOT disk durability. adv_delta_add (and the shared signal+readback family: gates.ts, spec-deltas.ts, wisdom.ts, tasks.ts, changes.ts) returns success after fireSignalWithMutationGuard confirms signal-in-history + reducer-applied via changeStateQuery readback — but then calls persistStateToDisk WITHOUT await (store-temporal/index.ts:219-250: `void (async()=>{...})()`, failure swallowed at debug). The disk projection is the SOLE source of truth once a workflow orphans (dead session queue), yet it's written fire-and-forget + swallow-on-failure. So success:true can be returned, the session can exit before the async changes.save flushes (or it fails silently), and the mutation becomes invisible to every disk-first reader (adv_delta_list/show, adv_change_show fallback) with no error. Durability model is inverted: the layer that must survive orphaning is written weakest. Not "signal-accept without persistence" — Temporal IS confirmed — but "confirmed Temporal persistence with unconfirmed best-effort disk persistence." Fix tracked in change gateMutationSuccessDisk (Epic hardenTemporalReliability entry 14): gate durable-mutation success on disk-projection durability (await + classify disk write, or invert to disk-authoritative writes). Sibling of rq-releaseProjectionDurability01 (read/terminal side) and Epic shell entry 6.
- **[gotcha]** Discovery (code-verified) — the disk-durability seam has a BROADER blast radius than the base fire-and-forget write. (1) Reducer dedup is correct (change-state.ts:1732-1768: applySpecDeltaAddedToState scans ALL capabilities and throws on duplicate delta.id). So the peer's improveCrossProject duplicate-ID acceptance (dl-q7m2Kp9xR4vB accepted twice) PROVES the authoritative workflow state did NOT retain delta#1 by request #2 — not merely a stale disk read. (2) Continue-as-new seed DOES include `deltas: state.deltas` (workflows.ts:1933), so CAN preserves deltas in the happy path — not the culprit. (3) Unifying mechanism: reseedChangeFromDisk (index.ts:585) reseeds with getCurrentSessionId (:636). If session A's unawaited fire-and-forget disk write hasn't flushed when session B reseeds an orphaned workflow, the rebuilt workflow LACKS delta#1 → duplicate add accepted → invisible with no error. The disk projection is BOTH the reseed source AND the weakest-guaranteed write. (4) reseedChangeFromDisk is GATED OUT on query_failed classification (index.ts:828-830) — a timing-out orphaned workflow cannot self-heal via reseed; disk-first reads bypass Temporal so they never trigger catch→reseed, and the signal path throws on SC4. (5) Live dogfooding this change: its own workflow orphaned on a dead prior-session queue; disk reads worked (40ms) while every Temporal query/signal timed out; OpenCode restart + OrphanQueueAdopter (10s heartbeat, FIFO) recovered it — confirming orphan-queue, not poisoned. Design implication: disk-first reads are the reliable layer under Temporal wedge → favors Direction 2 (disk-authoritative). SC4 tension: Direction 2 lets a mutation succeed on disk while the workflow is orphaned, which RELOCATES (not weakens) SC4's no-false-success guarantee from Temporal-readback to disk-fsync. Needs user steer.
- **[pattern]** FOLLOW-UP for Epic entry 6 (disk-authoritative reads/writes): concurrent-session projection serialization. Design validator (adv-researcher, 2026-07-23) found that await-own-write (this change, Direction 1) does NOT close two concurrent races: (#1 reseed-during-window) a peer session reseedChangeFromDisk-es from stale disk during another session's in-flight mutation; (#2 stale-overwrite) two sessions write the whole change.json from different readbacks — atomic rename prevents torn files but not stale last-writer-wins, so the disk projection can REGRESS even though the Temporal workflow stays monotonic. This is the concurrent-session generalization of the peer improveCrossProject duplicate-ID acceptance bug. Robust fix needs a monotonic generation or per-change cross-process lease/CAS. BLOCKER for a cheap in-place fix: change state has NO general per-mutation monotonic revision — acceptanceReadinessRevision advances only on acceptance-affecting mutations; Temporal historyLength resets at continue-as-new; lastSignalAt is a timestamp (equal-ms tie hole, P33). A proper fix must add a monotonic projectionRevision to the reducer + CAN seed + replay-determinism harness (the exact replay-sensitive surface that has repeatedly poisoned this Epic — treat with replay-determinism gating). User-approved Option A (2026-07-23): ship single-writer honesty here, defer concurrent-writer durability to entry 6. When entry 6 is planned: (a) add monotonic projectionRevision; (b) CAS-guard whole-file projection writes (write iff incoming >= on-disk generation); (c) make reseedChangeFromDisk participate in the same cross-process protocol so it never adopts a snapshot older than the workflow's known generation.
- **[convention]** For durability seams, a pure outcome-gate unit test (e.g. assertDurablePersist) is necessary but NOT sufficient: every durability-critical PUBLIC mutation path must have its own regression test proving that a post-ack disk-write failure rejects with the typed error (DiskProjectionPersistError) rather than returning success. Rationale (harden reviewer, gateMutationSuccessDisk): each caller independently awaits the durable helper; a future edit can silently restore success-before-disk-durability on one path while the pure-gate test + other paths stay green.
